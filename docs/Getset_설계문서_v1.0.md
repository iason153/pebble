## 1. 한 줄 정의

**Getset(겟셋) — 뭐부터 할지, 바로 정리.**
볼일이 몰린 날, 할 일만 넣으면 **동선(순서)과 현실적인 시간표, 끝나는 시각**까지 추천해 주는 도구.

| 항목 | 내용 |
|---|---|
| 서비스명 | Getset (겟셋) — "Get set, go!" 준비 끝, 출발 |
| 소속 | Pebble (오토컴퍼니) — 두 번째 툴 |
| 주소 | `pebbleitgo.com/getset/` (저장소 `getset/` 폴더 = URL) |
| 타깃 | 계획을 잘 세우지 않는 사람. 볼일이 여러 개 몰린 날 "뭐부터 하지?"로 막막한 사람 |
| 핵심 문장 | **내비는 "도착 시간"을 알려주지만, 사람에게 필요한 건 "일이 실제로 끝나는 시간"이다** |
| 난이도 | ★★★★ (Lineup ★★★보다 한 단계 위) |
| 배포 목표 | 착수 후 3~4주 |

## 2. 문제 정의 (논의 결론)

1. **뭐부터 할지 막막함** — 계획적인 사람은 하루를 설계하지만, 그렇지 않은 사람은 일정이 몰리면 순서를 못 정해 헤맨다.
2. **내비 시간 ≠ 실제 시간** — 내비는 도착 시각만 계산한다. 실제로는 **주차 자리 찾기 → 건물까지 걷기 → 엘리베이터 → 대기(번호표)** 같은 "도착 후 실질 시간"과 **볼일 자체의 체류 시간**, **차로 돌아가는 시간**이 더해진다. 볼일이 3~4개면 이 누락이 쌓여 하루 계획이 무너진다.
3. **시간 제약** — 병원 예약·미팅처럼 시각이 고정된 약속, 은행·관공서 마감 시각 때문에 순서가 제약된다.

### 2-1. 기존 서비스로 안 되는 이유 (2026-09-28 확인)

- **카카오맵/카카오내비**: 다중 경유지 길찾기는 입력한 순서 그대로만(최대 30곳). **경유지 순서 자동 최적화는 제휴사 전용**이며 오픈 API 미제공(카카오 데브톡 공식 답변).
- **구글 지도**: 순서 최적화 API가 있으나 유료이고, 한국은 구글의 자동차 길찾기 지원이 제한적.
- **해외 경로 최적화 앱**(Circuit, 경로 플래너 등): 택배 기사용, 영어·유료. "도착 후 실질 시간"이나 "체류 시간" 개념 없음.
- → **"순서 자동 추천 + 사람 시간(실질·체류) 계산 + 고정 약속 반영"을 한국 지도 앱과 연결해 주는 도구는 비어 있는 자리.**

## 3. 핵심 컨셉

Getset은 **길찾기 앱이 아니라 "하루 볼일 순서·시간 추천기"**다. 길 안내 자체는 이미 잘하는 카카오맵·네이버지도로 넘긴다(Lineup의 "튕김" 원칙과 동일).

```
① 할 일 넣기     장소 + 머무는 시간 (+ 예약 시각 / 마감 시각 / 먼저·마지막에)
      ↓
② 추천 받기      "이 순서로 가면 14:05에 끝나요 (여유 25분)"  + 추천 이유 한 줄
      ↓
③ 조정           끌어서 순서 변경 / 고정 → 즉시 재계산 (무리한 일정은 경고 + 대안)
      ↓
④ 출발           구간마다 카카오맵·네이버지도로 열기 / "도착"·"끝" 체크 → 학습
```

### 3-1. 결과 화면 예시

```
오늘 볼일 4개 · 9:10 출발 → 14:05 끝 (여유 25분)

 9:10  집 출발                         🚗
 9:28  ① 군포시청 도착 ─ 주차·이동 8분
 9:36  ~ 10:06  서류 발급 (30분)
10:14  ─ 차까지 8분
10:29  ② 은행 도착 ─ 주차·이동 5분      (마감 16:00 ✓)
       ...
13:30  ④ 치과  (예약 13:30 · 고정)      ← 이 시각에 맞춰 순서가 조정됨
14:05  끝

💡 치과 예약(13:30) 때문에 은행을 먼저 들러요
```

## 4. 현실 시간 모델 (Getset의 심장)

각 방문지 하나의 총 소요 = **이동 + 도착 후 실질 시간 + 머무는 시간 + 출발 준비 시간**

```
[이동: 길찾기/추정] → [도착 후 실질: 주차·도보·엘베·대기] → [머무는 시간: 볼일] → [출발 준비: 차로 복귀] → 다음
```

### 4-1. 장소 종류 × 이동수단별 기본값 (초안 — 대표 현실 감각으로 검토 필요)

단위: 분. "도착 후"=주차·건물 진입·엘베·접수 대기, "출발 준비"=차/정류장까지 복귀. 도보·대중교통은 주차가 빠지므로 값이 작다.

| 장소 종류 | 🚗 도착 후 | 🚗 출발 준비 | 🚶/🚌 도착 후 | 🚶/🚌 출발 준비 | 기본 머무는 시간 |
|---|---|---|---|---|---|
| 관공서·주민센터 | 8 | 5 | 3 | 1 | 20 |
| 은행 | 5 | 3 | 2 | 1 | 20 |
| 병원·의원 | 7 | 4 | 3 | 1 | 40 (대기 포함) |
| 대형마트·창고형 | 12 | 8 | 4 | 2 | 45 |
| 동네 마트·편의점 | 3 | 2 | 1 | 1 | 10 |
| 백화점·쇼핑몰 | 15 | 10 | 5 | 3 | 60 |
| 음식점·카페 | 6 | 4 | 2 | 1 | 50 |
| 우체국·택배 접수 | 5 | 3 | 2 | 1 | 15 |
| 학교·학원 픽업 | 5 | 2 | 2 | 1 | 10 |
| 도심 상가·사무실(빌딩) | 15 | 8 | 5 | 2 | 30 |
| 기타 | 7 | 4 | 3 | 1 | 30 |

- 장소 종류는 카카오 장소 검색 결과의 카테고리로 **자동 추정**, 사용자가 바꿀 수 있음.
- **사용자 커스텀**: ① 종류별 기본값 수정(내 기준) ② 특정 장소 개별 설정("이 병원은 대기 40분").

### 4-2. 학습 (v1 포함)

- 진행 중 각 방문지에서 **"도착" / "끝" 버튼** 두 번만 누르면 실제 시간이 기록된다.
  - 기록되는 값: 실제 이동 시간(이전 "끝" → 이번 "도착"), 실제 머문 시간("도착" → "끝")
  - "도착 후 실질 시간"은 머문 시간과 분리가 어려우므로 v1은 **"도착~끝 전체"**를 학습 단위로 사용하고, 머무는 시간 입력값과 비교해 실질 시간을 보정한다.
- 보정 방식: **장소별**(카카오 장소 ID 기준) → 없으면 **종류별** 순으로 적용. 지수이동평균(최근 기록 비중 30%)으로 천천히 수렴.
- 학습된 값에는 "내 기록 기준" 배지를 붙여 기본값과 구분.
- 저장: 기기 안(localStorage). 서버 전송 없음(Lineup과 동일 원칙).

## 5. 이동수단 (다양하게 — 동네 일정부터 장거리까지)

| 이동수단 | v1 방법 | 비용/한도 | 판단 |
|---|---|---|---|
| 🚗 자동차 | 카카오모빌리티 자동차 길찾기 API | **일 10,000회 무료**, 초과 시 1회 8원 | ✅ REST 키는 브라우저 노출 불가 → **서버리스 함수로 숨김**(§7) |
| 🚶 도보 | 직선거리 × 1.3(도로 우회 보정) ÷ 분당 70m | 없음 | ✅ 동네 거리에선 오차 작음. v2에서 TMAP 보행자 API 검토 |
| 🚲 자전거 | 직선거리 × 1.3 ÷ 분당 250m | 없음 | ✅ 추정 |
| 🚌 대중교통 | **추정**: 대기 8분 + 직선거리 × 1.4 ÷ 시속 20km + 도보 접근 6분 | 없음 | ⚠️ 정확도 한계 → "카카오맵에서 정확히 보기" 버튼 + **사용자가 실제 시간 수정 → 학습** |

- **구간별 이동수단**: 하루 기본 수단을 정하되, 800m 이내 구간은 자동 도보 제안, 구간마다 변경 가능.
- 대중교통 정확 API(ODsay 무료 하루 30회 수준·키 공개 불가 / TMAP 대중교통 유료)는 v1 제외, 이용량 보고 v2 판단.

### 5-1. 호출 수 절약 설계

- 순서 정하기는 **직선거리 기반 추정 시간**으로 계산(호출 0회).
- 추천 순서가 정해지면 **그 순서의 자동차 구간만** 실제 길찾기 호출(방문지 n곳 → n회).
- 실제 시간 반영 후 제약(예약·마감) 위반이 생기면 그때만 국소 재정렬 + 추가 호출. 같은 구간은 캐시(1시간).
- 예상: 1회 계획 ≈ 5~10회 호출 → 무료 1만 회로 하루 1,000~2,000건 계획 가능.

## 6. 추천 엔진 (순서 결정)

### 6-1. 입력

- 출발지(현재 위치/집/직접 검색), 출발 시각(지금/지정)
- 끝나는 곳: 출발지로 복귀 / 특정 장소 / 상관없음
- 방문지 목록: 장소, 종류, 머무는 시간, (선택) 고정 약속 시각, 마감 시각, "먼저/마지막에" 표시, 이동수단

### 6-2. 계산

- 방문지 **8곳 이하: 모든 순서를 전부 계산**(최대 40,320가지, 브라우저에서 즉시). 제약 위반 순서는 즉시 가지치기.
- **9~12곳**: 근사 알고리즘(가까운 곳 먼저 + 2-opt 개선 + 제약 위반 페널티).
- **13곳 이상**: v1에서는 제한(안내 문구). 볼일용 도구로 충분하다고 판단.
- 목적 함수: ① 모든 제약 충족 ② **가장 빨리 끝나는 순서** ③ 동률이면 이동 시간이 적은 순서.

### 6-3. 결과

- **추천안 1개가 기본**, "가장 빨리 끝남"과 "이동이 가장 적음"이 다르면 **둘 다 제시**하고 고르게 함.
- **추천 이유 한 줄**(예: "치과 예약 13:30 때문에 은행을 먼저 들러요", "마트는 '마지막에' 표시라 끝에 배치했어요").
- **무리한 일정 경고 + 대안**: "은행 마감 16:00에 12분 늦어요 → 은행을 먼저 가면 돼요" / 해결 불가 시 어느 일을 빼거나 미루면 되는지 제안.
- 끝나는 시각, **여유 시간**(고정 약속 사이 빈 시간 합) 표시.

### 6-4. 조정

- 순서를 끌어서 바꾸면 즉시 재계산(제약 위반 시 빨간 표시).
- "이 순서 고정" 잠금, "먼저/마지막에" 토글.

## 7. 기술 구조

| 항목 | 내용 | 비고 |
|---|---|---|
| 프론트 | HTML/CSS/JS, PWA (Lineup 구조 재사용) | 모바일 우선 표준 준수 |
| 장소 검색·지도 | **카카오맵 JavaScript SDK** (장소 검색 services.Places 포함) | JavaScript 키 + **도메인 제한**(pebbleitgo.com) → 브라우저 노출 OK |
| 자동차 길찾기 | 카카오모빌리티 길찾기 API | **REST 키 → 서버리스 함수**(`/api/route`)에서만 사용, 환경변수 보관 |
| 서버리스 함수 | 저장소 `api/route.js` (Vercel Functions) | 별도 서버 관리 없음. 캐시·호출 제한(IP당 분당 N회) 포함 |
| 저장 | localStorage (계획, 커스텀 기본값, 학습 기록) | 서버 저장 없음 |
| 지도 앱 넘기기 | `kakaomap://route?sp=위도,경도&ep=위도,경도&by=car\|foot\|publictransit\|bicycle` (웹 대체: `m.map.kakao.com/scheme/route?...`), 네이버지도 `nmap://route/...` | 카카오 경유지 vp~vp5(대중교통 제외). **구간 단위로 넘기는 것을 기본**으로 함 |
| 통계 | GA4 Pebble 속성 재사용 (`tool: getset`) | 장소명·좌표 전송 금지 |
| 공유·설치 | Lineup의 share.js / 설치 안내 시트 / 앱 안 브라우저 감지 재사용 | 모듈 공용화 검토 |

### 7-1. ⚠️ 호스팅 결정 필요 — Vercel 무료 요금제의 비상업 조항

- Vercel Hobby(무료)는 **"비상업·개인 용도만"** 허용(공식 문서 Fair Use Guidelines). **광고를 붙이면 상업 용도**가 된다.
- 이는 Getset뿐 아니라 **광고 자리를 계획 중인 Lineup·Pebble 전체**에 해당.
- 선택지:
  1. **Vercel Pro** ($20/월) — 지금 구조 그대로, 서버리스 함수 포함.
  2. **Cloudflare Pages + Workers** — 무료 요금제에서 상업 이용 가능, 정적 호스팅 + 함수(일 10만 요청 무료). 저장소 연결 방식 동일, 이전 작업 필요.
  3. 기존 EC2 — 서버 관리 부담(주 3시간 제약)과 충돌, 비추천.
- **권장**: 광고를 붙이기 전(Lineup 광고 자리 작업 전)에 결정. 비용 0원 유지가 목표면 2번, 손대지 않는 게 목표면 1번.
